# Структура Fullbox (актуально на 19.02.2026)

## 1. Архитектурный тип
Проект реализован как Django-монолит: единая кодовая база, единая БД и набор приложений по бизнес-доменам.

Сильная сторона текущего подхода: можно быстро вносить изменения в процессы и сразу выкатывать на прод.

Ограничение: при росте функционала увеличивается связность между модулями, а ошибки в расчётах статусов/остатков становятся дороже.

## 2. Карта модулей
### Роли и кабинеты
- `employees` + `employees/access.py` - роли, проверки доступа, маршрутизация по кабинетам.
- `client_cabinet` - кабинет клиента.
- `teammanager`, `head_manager`, `processing_head`, `processing_worker`, `sklad`, `reachtruck` - роль-ориентированные интерфейсы сотрудников.

### Процессы
- `orders` - приемка, акты, журнал заявок, базовые переходы статусов.
- `processing_app` - обработка товара, карты, раскоробовка, поток размещения, печать, техкарта.
- `sklad` - складской журнал, сводные остатки.
- `todo` - поручения и контроль исполнения.

### Справочники и объектные данные
- `sku` - клиенты (`Agency`), товары (`SKU`), ШК и фото.
- `market_sync` - настройки и синхронизация маркетплейсов.

### Маркировка и устройства
- `marking` - коды ЧЗ и их жизненный цикл.
- `agent` - агент сканера/печати, команды и события.
- `labels` - настройки печати/сканеров, связанная UI-логика.

### Служебный контур
- `audit` - общий аудит действий и заявок (`OrderAuditEntry`).
- `stockmap` - карта склада.

## 3. Ядро данных и текущая модель состояния
Ключевая точка правды по заявкам: `audit.OrderAuditEntry`.

То есть фактическое состояние процесса в большинстве экранов строится не из отдельной нормализованной модели заказа, а как реконструкция из событий (payload JSON в аудит-ленте).

Это позволяет быстро расширять сценарии, но накладывает требования:
- единые правила агрегации должны быть в одном месте;
- любые дубли в логике расчёта легко дают расхождения остатков.

## 4. Что уже хорошо
- Ролевая модель в явном виде.
- Прозрачная история действий по заявкам.
- Быстрый цикл «исправил -> задеплоил -> проверил».
- Интеграция с агентом сканера и печати уже встроена в процессы.
- Поддержка ЧЗ, печатных форм и потоковых операций в одной системе.

## 5. Замечания и риски
- Два самых крупных файла (`processing_app/views.py`, `orders/views.py`) стали узкими местами поддержки.
- Бизнес-правила по остаткам/статусам исторически дублировались в нескольких модулях.
- Тестовое покрытие сейчас почти отсутствует (в большинстве apps `tests.py` заглушки).
- Часть бизнес-сущностей фактически живёт внутри JSON payload и требует аккуратной миграции при усложнении логики.

## 6. Рекомендации (приоритет)
### A. Зафиксировать доменную модель движения товара
Ввести явную модель движений (ledger) с обязательными полями:
- источник операции,
- тип операции (приход/перемещение/обработка/списание/возврат),
- количество,
- тип товара (оптовый/готовый/...),
- место (зона/палета/короб),
- ссылка на документ/заявку.

Это снизит зависимость от реконструкции через разные payload.

### B. Вынести расчёт остатков в единый сервис
Один модуль расчёта остатков должен использоваться всеми экранами:
- складские остатки,
- выбор товара в обработку,
- журнал движения,
- клиентский кабинет.

### C. Накрыть критический путь интеграционными тестами
Минимальный набор сценариев:
- приемка -> размещение;
- частичный отбор в обработку;
- обработка -> размещение -> завершение;
- контроль ЧЗ по коробам;
- проверка расхождений и акт разногласий.

## 7. Практический next step
Сформировать технический RFC на 2-3 страницы:
- текущая схема данных,
- целевая схема движения,
- пошаговый план миграции без остановки процессов.

Это позволит развивать систему дальше без повторных перекосов в остатках и статусах.

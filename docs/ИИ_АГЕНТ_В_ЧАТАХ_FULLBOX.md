# Дополнение к единому промпту: ИИ-агент в чатах FullBox

Полная спецификация (§39–§63). Краткое правило для Cursor: `.cursor/rules/chats-ai-agent.mdc`.

────────────────────────────────────────
39. ИИ-АГЕНТ FULLBOX
────────────────────────────────────────

Сразу заложить в архитектуру чатов возможность подключения ИИ-агента FullBox.

ИИ-агент должен работать внутри существующего модуля сообщений и помогать:

- клиентам получать быстрые ответы;
- менеджерам готовить ответы;
- складу находить инструкции;
- руководителям анализировать обращения;
- автоматически классифицировать вопросы;
- связывать сообщения с заявками, задачами и объектами WMS.

На первом этапе ИИ не должен бесконтрольно отправлять ответы клиентам.

Основной режим первого этапа:
«ИИ предлагает ответ — сотрудник проверяет — сотрудник отправляет».

Автоматические ответы разрешать только для заранее утверждённых сценариев и после отдельного включения администратором.

Не изменять складские данные, остатки, статусы заявок, биллинг и документы только на основании решения ИИ.

────────────────────────────────────────
40. РЕЖИМЫ РАБОТЫ ИИ
────────────────────────────────────────

## 40.1. ИИ-помощник менеджера

ИИ:

- читает текущую переписку;
- учитывает клиента;
- учитывает связанную заявку;
- находит информацию в базе знаний;
- получает разрешённые данные из WMS;
- предлагает черновик ответа;
- указывает использованные источники;
- показывает уровень уверенности;
- предлагает следующее действие.

Менеджер может:

- принять ответ;
- отредактировать;
- отклонить;
- попросить другой вариант;
- сделать ответ короче;
- изменить тон;
- добавить ответ в базу знаний.

ИИ не отправляет черновик клиенту без действия менеджера.

## 40.2. ИИ-консультант клиента

После тестирования разрешить автоматические ответы на безопасные вопросы:

- как создать заявку;
- где посмотреть остатки;
- какие форматы файлов поддерживаются;
- как загрузить номенклатуру;
- где скачать акт или счёт;
- что означает статус заявки;
- как связаться с менеджером;
- какие документы необходимы;
- как работает приёмка;
- как посмотреть связанные заявки.

Для ответа по конкретной заявке ИИ должен получать данные через разрешённый backend API, а не придумывать их.

## 40.3. Внутренний ИИ-помощник FullBox

Для сотрудников:

- поиск по регламентам;
- инструкции по приёмке / обработке / маркировке / ЧЗ / оборудованию;
- порядок действий при расхождениях;
- поиск по внутренней базе знаний;
- краткое резюме длинной переписки;
- создание черновика задачи;
- определение ответственного подразделения.

Внутренние данные нельзя показывать клиенту.

────────────────────────────────────────
41. ПРАВИЛЬНЫЙ ПОДХОД К «ОБУЧЕНИЮ»
────────────────────────────────────────

Не реализовывать неконтролируемое самообучение модели на каждой переписке.

На первом этапе использовать:

- базу знаний;
- RAG-поиск;
- векторный поиск;
- подтверждённые ответы сотрудников;
- обратную связь менеджеров;
- историю успешных решений;
- утверждённые шаблоны;
- данные WMS через безопасные API.

Для существующего PostgreSQL рассмотреть pgvector, если совместимо с архитектурой.

Fine-tuning — только после накопления качественной выборки, очистки ПДн, проверки, классификации, утверждения руководителем и отдельного тестирования.

────────────────────────────────────────
42. ИСТОЧНИКИ ЗНАНИЙ ИИ
────────────────────────────────────────

## 42.1. Общая база знаний FullBox

Инструкции, регламенты, FAQ, статусы, документы, маркетплейсы, упаковка, маркировка, ЧЗ, утверждённые шаблоны.

## 42.2. Данные конкретного клиента

Только при наличии прав: договор, тарифы, КП, реквизиты, заявки, остатки, документы, история, менеджер.

ИИ не должен смешивать данные разных клиентов.

## 42.3. Данные заявки

Номер, тип, статус, сроки, ответственные, задачи, расхождения, файлы, системная история, разрешённые комментарии.

## 42.4. Подтверждённые диалоги

Только ответы, которые отправлены сотрудником, не удалены, не отмечены ошибочными, получили положительную оценку и разрешены для базы знаний.

────────────────────────────────────────
43. ИЗОЛЯЦИЯ ДАННЫХ КЛИЕНТОВ
────────────────────────────────────────

Обязателен tenant isolation.

В контекст ИИ передавать: user_id, agency_id, thread_id, order_id, роль, permissions.

Запрещено искать/показывать данные других клиентов, чужие тарифы/остатки/документы/переписку, смешивать внутреннюю и клиентскую БЗ.

Проверку выполнять на backend до отправки данных в ИИ-сервис. Не полагаться только на системный промпт.

────────────────────────────────────────
44. ИНТЕРФЕЙС ИИ В ЧАТЕ
────────────────────────────────────────

В поле сообщения менеджера — кнопка «Предложить ответ».

Карточка «Черновик ИИ»: текст, уверенность, источники, предупреждения, связанные данные; кнопки «Вставить», «Отправить», «Изменить», «Другой вариант», «Отклонить».

Черновик не выглядит как отправленное сообщение.

Автоответ клиенту помечать: «Ответ ИИ-помощника FullBox». Ответ, подтверждённый менеджером — обычное сообщение менеджера.

Индикатор «ИИ готовит ответ…» без блокировки UI.

────────────────────────────────────────
45. КНОПКИ БЫСТРЫХ ДЕЙСТВИЙ ИИ
────────────────────────────────────────

Компактное меню «ИИ-помощник»: сформировать ответ; короче / понятнее / официальнее / дружелюбнее; исправить ошибки; перевести; резюме; нерешённые вопросы; создать задачу; ответственный; связанная заявка; регламент; следующий шаг.

Не выводить все действия одновременно.

────────────────────────────────────────
46. КЛАССИФИКАЦИЯ ОБРАЩЕНИЙ
────────────────────────────────────────

Темы: приёмка, обработка, отгрузка, остатки, биллинг, тарифы, документы, расхождения, брак, ЧЗ, маркировка, логистика, маркетплейсы, техошибка, претензия, другое.

Также: срочность, тональность, необходимость ответа, подразделение, номер заявки/SKU/короба, финансы, конфликт.

Классификация сама не меняет бизнес-объекты без подтверждения или утверждённого правила.

────────────────────────────────────────
47. УРОВЕНЬ УВЕРЕННОСТИ
────────────────────────────────────────

Высокая / средняя / низкая.

При низкой — не выдумывать: уточнить, передать сотруднику, создать задачу, показать менеджеру, чего не хватает.

Клиенту: «Для точного ответа подключаю менеджера FullBox».

────────────────────────────────────────
48. ОБЯЗАТЕЛЬНЫЕ ОГРАНИЧЕНИЯ ИИ
────────────────────────────────────────

ИИ запрещено самостоятельно менять остатки, движения, ячейки, количества, подтверждать приёмку/обработку/отгрузку, закрывать заявки, менять тарифы, выставлять счета/акты/УПД, обещать даты без данных, давать скидки, менять договор, признавать ответственность, передавать внутреннюю переписку клиенту.

Любое действие: права → подтверждение сотрудника → backend WMS → аудит.

────────────────────────────────────────
49. АВТОМАТИЧЕСКИЕ ОТВЕТЫ
────────────────────────────────────────

Включаются отдельно администратором. Белый список тем.

Разрешено (пример): приветствие, подтверждение получения, рабочее время, инструкция создания заявки, ссылка на остатки, описание статуса, передача менеджеру, запрос номера заявки/SKU/документа.

Запрещено авто: претензии, тарифы/стоимость, расхождения, недостача, повреждение, компенсация, договор, задолженность, юридическое, спорные сроки, ПДн, изменение складской операции.

────────────────────────────────────────
50. ПЕРЕДАЧА ДИАЛОГА СОТРУДНИКУ
────────────────────────────────────────

Эскалация при: нет точного ответа; низкая уверенность; просьба сотрудника; повтор вопроса; претензия; деньги; расхождение; склад; изменение заявки; недовольство; ИИ дважды не помог.

При передаче: назначить ответственного, уведомить, резюме, что спрашивал клиент, найденные заявки, нерешённый вопрос, статус «Требует ответа FullBox».

────────────────────────────────────────
51. ОБРАТНАЯ СВЯЗЬ И ОБУЧЕНИЕ
────────────────────────────────────────

Сохранять: вопрос, контекст, предложенный ответ, источники, уверенность, принял/изменил/отправил, оценки, итог.

Оценка менеджера: полезно / частично / неверно / устарело / не тот источник / нельзя авто.

Не добавлять в БЗ автоматически после одной отправки. Очередь модерации «Кандидаты в базу знаний».

────────────────────────────────────────
52. БАЗА ЗНАНИЙ ИИ
────────────────────────────────────────

Админ-раздел «ИИ и база знаний»: документы, FAQ, инструкции, утверждённые ответы, кандидаты, источники, категории, версии, неактуальное, ошибки, аналитика.

Поля записи: название, текст, категория, доступность клиент/сотрудник, клиент (если индивидуальный), автор, дата утверждения, срок, версия, источник, статус модерации.

Статусы: Черновик / На проверке / Утверждено / Требует обновления / Архив.

────────────────────────────────────────
53. ИСТОЧНИКИ В ОТВЕТЕ
────────────────────────────────────────

Менеджеру показывать источники со ссылкой «Открыть источник».

Клиенту — компактно и без внутренних документов.

────────────────────────────────────────
54. КОНТЕКСТ КЛИЕНТА
────────────────────────────────────────

Учитывать компанию, менеджера, заявки, тарифы, услуги, МП, историю — только при доступе.

Тарифы всегда из backend, не как постоянное знание в промпте.

────────────────────────────────────────
55. ИНТЕГРАЦИЯ С WMS
────────────────────────────────────────

Безопасный слой инструментов без прямого доступа к БД, например:

- get_client_orders;
- get_order_status;
- get_client_stock;
- get_order_documents;
- get_assigned_manager;
- search_knowledge_base;
- create_task_draft;
- prepare_message_draft.

Каждый инструмент: auth, роль, клиент, ограничение полей, аудит, структура, без опасных изменений без подтверждения.

────────────────────────────────────────
56. АРХИТЕКТУРА ИИ-СЕРВИСА
────────────────────────────────────────

Не размещать всю логику в Django view.

Слой:

- AIOrchestrator;
- KnowledgeSearchService;
- AIConversationService;
- AIActionPolicy;
- AIResponseValidator;
- AIAuditService.

Выход структурированный: текст, категория, уверенность, источники, действия, эскалация, предупреждения, разрешён_ли_автоответ.

Критические решения не принимать по свободному тексту модели.

────────────────────────────────────────
57. БЕЗОПАСНОСТЬ ИИ
────────────────────────────────────────

Защита от prompt injection, утечки внутренних инструкций/чужих данных, вредоносных документов, подмены правил, утечки ПДн/договоров/тарифов, неразрешённых действий.

Текст клиента и файлы — недоверенные. Документ из чата не становится источником БЗ без модерации.

────────────────────────────────────────
58. ПЕРСОНАЛЬНЫЕ И КОНФИДЕНЦИАЛЬНЫЕ ДАННЫЕ
────────────────────────────────────────

Перед внешней моделью: допустимость, маскирование, договор, журнал.

Маскировать телефоны, email, паспорт, банк, ПДн сотрудников, ключи, токены, пароли.

Никогда не передавать пароли, API-ключи, секреты, полные платёжные данные, недоступные документы.

────────────────────────────────────────
59. АНАЛИТИКА ИИ
────────────────────────────────────────

В кабинете руководителя: объём, ИИ / эскалация, принятые черновики, % правок, время ответа, доля авто, полезность, ошибки, пробелы БЗ, экономия времени, низкая уверенность; отдельно жалобы, без источников, исправленные, повторные вопросы.

────────────────────────────────────────
60. ЭТАПЫ ЗАПУСКА ИИ
────────────────────────────────────────

1. Сбор и подготовка — БЗ, индекс, права, фидбек; ИИ не отвечает клиенту.
2. Copilot менеджера — черновики, правки, аналитика.
3. Автоответы FAQ — белый список, высокая уверенность, источники, эскалация.
4. Маршрутизация — подразделение, черновик задачи, резюме, SLA.
5. Ограниченные действия — только safe API + подтверждение + аудит.

Не переходить дальше без тестов предыдущего этапа.

────────────────────────────────────────
61. ТЕСТИРОВАНИЕ ИИ
────────────────────────────────────────

Набор: типовые / неоднозначные / без ответа / чужие данные / изменить остатки / претензия / тариф / заявка / неверный номер / внутренняя инструкция / injection / конфликт / повтор / устаревшее.

Проверять точность, источники, права, отсутствие выдумок, эскалацию, утечки, опасные действия, tenant, отсутствие данных.

Эталонный набор прогонять после каждого изменения логики или БЗ.

────────────────────────────────────────
62. ВИЗУАЛЬНЫЕ СОСТОЯНИЯ ИИ
────────────────────────────────────────

Выключен; анализирует; готовит черновик; готов; источники; низкая уверенность; уточнение; передан менеджеру; авто разрешён/запрещён; ошибка; недоступен; отклонён; исправлен; в модерации.

При недоступности ИИ обычный чат работает без ошибок.

────────────────────────────────────────
63. КРИТЕРИИ ГОТОВНОСТИ ИИ-МОДУЛЯ
────────────────────────────────────────

Не ломает чат; отдельный сервисный слой; права; tenant; источники; уверенность; эскалация; нет опасных действий; фидбек; модерация; аудит; аналитика; security-тесты; выключается админом; при отказе ИИ чат жив.

## Финальное требование

Сразу заложить архитектуру, запускать постепенно.

Этап 1: помощник менеджера (черновик → проверка → отправка).

Не создавать неконтролируемого самообучающегося бота.

Обучение: подтверждённые ответы, фидбек, модерация, БЗ, RAG, тестовый набор, контроль качества.

Автоответы клиентам — только белый список + высокая уверенность + подтверждённый источник + флаг админа.

## Как запускать (операционный план)

| Когда | Что |
|---|---|
| Сейчас | Модели, API, журнал ответов ИИ, база знаний, pgvector (если ок), кнопка «Предложить ответ» |
| После накопления переписки | Черновики для менеджеров |
| После проверки качества | Авто на FAQ / статус / инструкции / остатки через API |
| Никогда без человека | Тарифы, претензии, недостачи, компенсации, изменения заявок, закрытие операций, движения товара |

## Каркас в коде (этап 1, stub)

Уже заложено локально:

- модели: `ChatAISettings`, `ChatAISuggestion`, `ChatAIKnowledgeCandidate` (`0011_chat_ai_foundation`)
- слой: `client_cabinet/chat_ai/` (`AIOrchestrator` stub, `AIActionPolicy`, knowledge stub)
- API: `POST /team-manager/api/chats/<id>/ai/suggest/`, `.../ai/suggestions/<id>/feedback/`
- UI менеджера: кнопка «Предложить ответ» + карточка «Черновик ИИ»
- автоответ клиенту всегда `false`; склад к API не допускается

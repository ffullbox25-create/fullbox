# План действий: отдельный сервис ричтракера OTG

## Цель

Сделать отдельное приложение/сервис планирования доставки товара в зону OTG для заявок на отгрузку, не переписывая старый сервис ричтракера и не меняя работу водителя.

Для водителя ричтрака процесс остается прежним: он получает задание, видит паллету/ячейку/OTG, сканирует паллету или короба и завершает перемещение. Ему не важно, старый сервис сформировал задание или новый OTG-сервис.

## Что сейчас важно сохранить

- Клиент при создании заявки на отгрузку выбирает товар из складских остатков.
- Основной выбор идет коробами: сколько коробов конкретного состава надо отгрузить.
- Для обычного короба состав состоит из одной товарной строки.
- Для микс-короба состав состоит из нескольких товарных строк.
- Редкое исключение - разбивка короба, когда из физического короба забирают не весь состав.
- Старый водительский интерфейс ричтрака должен продолжать получать привычные задания.
- Старый сервис ричтракера не правим глубоко; новый OTG-сервис подключаем рядом.

## Главный контракт OTG-сервиса

OTG-сервис должен получать не просто `sku + qty`, а коробочную потребность:

```text
заявка на отгрузку -> состав короба -> сколько физических коробов такого состава нужно привезти в OTG
```

Пример обычного короба:

```json
{
  "box_composition": [
    {
      "sku": "SKU-1",
      "barcode": "111",
      "size": "M",
      "goods_type": "Товар",
      "qty_per_box": 12
    }
  ],
  "boxes_required": 37,
  "is_mixed": false
}
```

Пример микс-короба:

```json
{
  "box_composition": [
    {
      "sku": "SKU-1",
      "barcode": "111",
      "size": "M",
      "goods_type": "Товар",
      "qty_per_box": 4
    },
    {
      "sku": "SKU-2",
      "barcode": "222",
      "size": "L",
      "goods_type": "Товар",
      "qty_per_box": 8
    }
  ],
  "boxes_required": 3,
  "is_mixed": true
}
```

## Что должен сформировать OTG-сервис для ричтракера

OTG-сервис сам выбирает паллеты и создает исполнимые задания.

Тип 1: привезти паллету целиком.

```json
{
  "task_type": "full_pallet_to_otg",
  "shipping_order": "SO-000123",
  "pallet_code": "PAL-001",
  "from_location": "A-01-01",
  "to_zone": "OTG",
  "box_composition": [],
  "boxes_count": 10
}
```

Водитель берет паллету целиком и везет в OTG. Короба внутри паллеты по одному не пикаются.

Тип 2: добрать часть коробов с назначенной паллеты.

```json
{
  "task_type": "pick_boxes_from_pallet_to_otg",
  "shipping_order": "SO-000123",
  "pallet_code": "PAL-004",
  "from_location": "A-01-04",
  "to_zone": "OTG",
  "selection_mode": "any_matching_box",
  "boxes_required": 7,
  "box_composition": []
}
```

Водителю уже назначена паллета. Если на ней 10 одинаковых коробов, а нужно 7, водитель может сканировать любые 7 из 10 в любой последовательности. Система фиксирует каждый просканированный короб как отправленный в OTG по этой заявке.

## Базовый алгоритм планирования

Для каждой коробочной потребности:

1. Найти на складе физические короба с точно таким же составом.
2. Сгруппировать найденные короба по паллетам.
3. Сначала выбрать паллеты, которые можно отвезти целиком.
4. Полной паллетой считать паллету, где весь доступный товар подходит под текущую коробочную потребность и количество коробов не превышает потребность.
5. После полных паллет посчитать остаток коробов.
6. Остаток добрать с одной или нескольких назначенных паллет.
7. Для добора с частичной паллеты не назначать конкретные box-code заранее, если все подходящие короба одинаковые.
8. Конкретные box-code фиксировать в момент скана водителем.
9. Не давать водителю выбирать паллету: выбор паллет делает OTG-сервис.

Пример:

```text
Нужно 37 коробов состава A.
На складе 5 паллет по 10 коробов состава A.

План:
1. PAL-001 целиком: 10 коробов
2. PAL-002 целиком: 10 коробов
3. PAL-003 целиком: 10 коробов
4. PAL-004: добрать любые 7 из 10 коробов состава A
```

## Отдельные правила

- Единица планирования - физический короб конкретного состава.
- `qty_requested` в штуках не должен быть главным входом планировщика.
- Кратность нужна как часть состава короба.
- Миксованность должна передаваться явно через состав короба, а не угадываться из текста.
- Разбор короба должен идти отдельным типом исключения.
- Если товар нельзя собрать коробами нужного состава, OTG-сервис должен вернуть блокировку/ошибку планирования, а не молча перейти на подбор штуками.
- Если паллета уже в активной задаче ричтрака, ее нельзя выбирать для нового OTG-плана.
- Если короб уже в OTG или в процессе движения в OTG по этой заявке, его нельзя планировать повторно.

## Предлагаемая структура нового приложения

Приложение: `otg_reachtruck`.

Основные сущности:

- `OtgDeliveryRequest` - заявка OTG на доставку товара по отгрузке.
- `OtgDeliveryDemand` - потребность: состав короба и сколько таких коробов нужно.
- `OtgPalletPlan` - выбранная паллета в плане.
- `OtgPickTask` - логическая задача OTG-сервиса.
- `OtgBoxClaim` - фиксация конкретного box-code при скане, особенно для частичного добора.
- `OtgPlanningEvent` - журнал решений планировщика.

Статусы:

- `requested` - создана потребность OTG.
- `planning` - идет планирование.
- `planned` - план построен.
- `dispatched` - задания переданы в текущий ричтракер.
- `in_progress` - водитель выполняет задания.
- `partial` - часть доставлена, есть остаток или проблема.
- `done` - все доставлено в OTG.
- `blocked` - невозможно спланировать.
- `canceled` - отменено.

## Интеграция со старым ричтракером

Новый OTG-сервис должен создавать на выходе привычные `MoveRequest` и `MoveTask`, чтобы водительский интерфейс не менялся.

Старый путь:

```text
shipping -> reachtruck.create_shipping_pick_request -> MoveRequest/MoveTask
```

Новый путь:

```text
shipping -> otg_reachtruck -> OTG-план -> MoveRequest/MoveTask
```

На первом этапе желательно оставить переключатель:

```text
USE_OTG_REACHTRUCK_PLANNER = false/true
```

При выключенном флаге работает старый путь. При включенном - новый OTG-планировщик.

## Этапы внедрения

### Этап 1. Подготовка данных

1. Описать нормализованную коробочную потребность из `ShippingOrderItem`.
2. Перестать полагаться только на текстовый `comment` как на источник истины.
3. Сделать функцию, которая из заявки отгрузки строит список `box_composition + boxes_required`.
4. Покрыть тестами обычные короба, микс-короба и split-исключения.

### Этап 2. Shadow-планирование

1. Создать приложение `otg_reachtruck`.
2. Добавить модели OTG-заявки и OTG-плана.
3. При команде "Дать ричтраку доставку в OTG" строить новый OTG-план, но пока не отдавать его водителю.
4. Логировать результат рядом со старым планом.
5. Сравнить старый и новый план на реальных сценариях.

### Этап 3. Создание заданий через новый сервис

1. Подключить флаг `USE_OTG_REACHTRUCK_PLANNER`.
2. При включенном флаге создавать `MoveRequest/MoveTask` из OTG-плана.
3. Для полных паллет создавать задачи "паллету целиком в OTG".
4. Для остатка создавать задачи "с назначенной паллеты взять N подходящих коробов".
5. Сохранить совместимость payload с текущим мобильным интерфейсом ричтрака.

### Этап 4. Исполнение и фиксация сканов

1. Для полной паллеты переводить всю паллету/ее короба в OTG без попиковой приемки каждого короба.
2. Для частичной паллеты фиксировать каждый просканированный box-code.
3. Проверять, что просканированный короб соответствует требуемому составу.
4. После каждого скана отмечать короб как движущийся/доставленный в OTG по заявке.
5. Закрывать задачу, когда набрано нужное количество коробов.

### Этап 5. Переключение

1. Включить новый OTG-планировщик сначала на тестовом сценарии.
2. Проверить водительский экран.
3. Проверить складские состояния после полной паллеты.
4. Проверить складские состояния после добора 7 из 10.
5. Проверить повторный запуск, чтобы не создавались дубли.
6. После подтверждения включить для рабочего процесса.

## Тестовые сценарии

- Нужно 37 коробов, на складе 5 паллет по 10 одинаковых коробов: план 3 полные паллеты + 7 коробов с четвертой.
- Нужно 20 коробов, на складе 2 паллеты по 10: план 2 полные паллеты.
- Нужно 7 коробов, на складе 1 паллета 10: план частичного добора 7 из 10.
- Нужно 3 микс-короба: планируется коробочный состав из нескольких строк.
- Клиент выбрал split-разбор короба: планируется отдельное исключение.
- Одна паллета уже занята активной задачей: планировщик ее пропускает.
- Часть коробов уже в OTG: планировщик не создает повторную доставку.
- Повторное нажатие "Дать ричтраку доставку в OTG" не создает дубли заданий.

## Риски и защита

- Риск: новый планировщик выберет не те короба.
  Защита: проверять точный состав короба перед планированием и перед сканом.

- Риск: дубли задач после повторного запуска.
  Защита: идемпотентный `OtgDeliveryRequest` на одну shipping-заявку и активные статусы.

- Риск: водительский интерфейс сломается.
  Защита: на выходе формировать привычные `MoveRequest/MoveTask` и не менять экран водителя.

- Риск: старый сервис нужен для отката.
  Защита: флаг переключения на старый путь.

- Риск: split-разбор короба смешается с обычным подбором коробами.
  Защита: split держать отдельным типом планирования и требовать явного подтверждения.

## Критерий готовности

Новый OTG-сервис считается готовым, когда:

- из заявки отгрузки строится коробочная потребность по составу;
- планировщик выбирает паллеты сам;
- сначала выбираются полные паллеты;
- остаток добирается с назначенной паллеты;
- водительский интерфейс не изменился;
- сканы коробов фиксируют доставку в OTG;
- повторный запуск не создает дубли;
- есть быстрый откат на старый путь.
